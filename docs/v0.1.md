# Plan de la v0.1

> Objectif : remplacer le terminal habituel pour lancer, suivre et reprendre des sessions Claude Code, avec les deux profils, et répondre aux permissions sans chercher le bon terminal.
> Références : [architecture](architecture.md), ADR [0001](adr/0001-demon-orchd.md) à [0004](adr/0004-front-electron.md), [maquette](../prototype/orchestrateur.html).

## Périmètre

**Dans la v0.1**

- Lancer une session dans un projet (dossier existant ou worktree existant), avec un profil, un modèle, un mode et un prompt initial libre.
- Reprendre une session : celles lancées par l'app, et les anciennes trouvées dans les transcripts des deux profils.
- Vue par projet : projets regroupés par dépôt git, sessions avec statut, branche, profil, dernière activité.
- Vue d'une session : terminal (le vrai `claude`), en-tête avec mode (modifiable), contexte, coût, tokens, dernière activité.
- Statuts : en cours, à répondre (permission ou question), inactive, arrêtée, erreur.
- Répondre depuis l'app : permissions (Autoriser, Toujours pour ce projet, Refuser) et questions de Claude (`AskUserQuestion`).
- Quotas 5 h et hebdo par profil (statusline, endpoint non documenté en repli).
- Notifications desktop quand une session attend une réponse.
- Thèmes clair, sombre, auto, et palettes (dont Okabe-Ito), couleurs personnalisables.

**Hors v0.1** (versions suivantes) : vue par statut, diff et revue, onglet Fichiers, issues GitHub, création et nettoyage de worktrees, runners et aperçu web, livraison et CI, sous-agents, dictée, plugins, SSH.

## Choix techniques de la v0.1

| Sujet | Choix |
|---|---|
| Démon | Rust, `tokio`, PTY via `portable-pty`, émulateur sans affichage `vt100` (son rendu ANSI de l'écran sert à restaurer un terminal à la reconnexion), SQLite via `rusqlite` |
| Relais | sous-commandes `orchd hook <événement>` et `orchd statusline` du même binaire |
| Protocole | socket Unix `$XDG_RUNTIME_DIR/devmaestro/orchd.sock`, trames préfixées par leur longueur : JSON-RPC 2.0 ou octets PTY |
| Front | Electron + Vite + React + TypeScript, xterm.js (WebGL), gestionnaire de paquets `pnpm` |
| Tests | domaine : tests unitaires rejouant les jeux d'événements réels du prototype n° 1 ; démon : tests d'intégration avec un faux `claude` (script qui imite la TUI et appelle les hooks) ; front : tests unitaires de la logique d'affichage |

Toutes les versions de dépendances sont vérifiées sur le registre au moment de les ajouter.

## Lots

Chaque lot suit le même cycle : implémentation par un sous-agent, relecture critique par un agent indépendant, corrections, vérification (diff et tests), commit.

| Lot | Contenu | Terminé quand |
|---|---|---|
| **1. Socle et domaine** | Workspace Rust (`crates/core`), modèle de domaine (profil, projet, session), machine à états des sessions, détection des profils, lecture tolérante des transcripts | La machine à états passe sur les jeux d'événements réels du prototype n° 1 ; `cargo test`, `clippy`, `fmt` au vert |
| **2. Démon et sessions** | `orchd` : socket et protocole, lancement et reprise de sessions dans des PTY, émulateur et tampon, plugin de hooks et statusline chaînée générés, relais `orchd hook` / `orchd statusline`, SQLite | Test d'intégration avec un faux `claude` : lancement, événements, statut, reprise, reconnexion d'un client qui retrouve l'écran |
| **3. Permissions et questions** | `PermissionRequest` bloquant, deux canaux concurrents (app et TUI), réponse aux `AskUserQuestion` par `updatedInput.answers`, changement de mode par Shift+Tab vérifié | Tests d'intégration couvrant les cas du prototype n° 1 (réponse app, réponse TUI, délai dépassé) |
| **4. Front Electron** | Squelette Electron sécurisé, client du démon dans le processus principal, vue par projet, vue session avec xterm.js, en-tête, cartes de permission et de question | L'app lance une vraie session, l'affiche et permet d'y répondre ; tests du front au vert |
| **5. Quotas, notifications, thèmes, nouvelle session** | Jauges par profil, notifications desktop, thèmes et palettes, fenêtre « Nouvelle session » (projet, profil, modèle, mode, prompt, reprise) | Démonstration de bout en bout sur le poste de référence, avec les deux profils |

## Critères de fin de la v0.1

- Lancer, suivre et reprendre une session avec chacun des deux profils.
- Une permission et une question de Claude répondues depuis l'app, la TUI restant utilisable.
- Fermer et rouvrir l'app sans perdre de session ni l'écran des terminaux.
- Les hooks de l'utilisateur (peon-ping) et sa statusline continuent de fonctionner.
- CPU de l'app au repos proche de zéro ; une session qui travaille reste sous ~20 % d'un cœur (mesuré avec le banc du prototype n° 2 si besoin).

## Questions ouvertes (relevées pendant les lots)

- **Prompt initial en argument** : `--` est placé avant le prompt pour qu'un texte commençant par `-` ne soit pas lu comme une option. Reste à vérifier avec le vrai CLI que `--` est accepté, et qu'un prompt égal au nom d'une sous-commande (`update`, `mcp`…) n'est pas exécuté comme telle. Si c'est le cas : envoyer le prompt initial dans la TUI (collage) après `SessionStart` au lieu de le passer en argument.
- **Arrêt d'une session** : le vrai `claude` émet-il un `SessionEnd` sur SIGHUP, ou faut-il attendre le SIGKILL après 3 s ?
- **Interruption par Échap** sur une demande ouverte, et `idle_prompt` pendant un dialogue ouvert : comportement réel à observer (la machine à états marque ces demandes « peut-être obsolètes »).
- **Sécurité du démon** (relevé par une revue de sécurité automatique du lot 2) : une session `claude` détournée pourrait parler au démon avec les droits de l'utilisateur. Le lot 3 sépare le socket des relais du socket de contrôle, vérifie l'identité du processus client et refuse les modes `bypassPermissions` / `dontAsk` sauf réglage explicite. C'est une atténuation, pas un bac à sable : à compléter par un ADR sur le modèle de menace avant la v1.
- **Refus depuis l'app** (lot 3) : après un `deny` renvoyé par le hook `PermissionRequest`, quel hook le vrai CLI émet-il (`PermissionDenied`, `PostToolUseFailure`, aucun) ? La demande est déjà close côté démon (`answered_by_app`) ; à observer pour la machine à états.
- **Réponses à choix multiples** (lot 3) : la documentation dit « joints par des virgules » ; le démon envoie `"Rouge, Vert"`. À vérifier avec le vrai CLI (le prototype n° 1 n'a testé qu'un choix simple).
- **Cycle de Shift+Tab** (lot 3) : relevé sur 2.1.303 (`manual` → `accept edits` → `plan` → `auto`). Il dépend peut-être des modes disponibles (`auto` absent sur certains comptes, `bypassPermissions` ajouté avec `--allow-dangerously-skip-permissions`) : `sessions.setMode` vérifie a posteriori par le hook suivant, mais ne corrige pas un compte faux.
- **Relais `PermissionRequest` tué par Claude Code** : si la TUI répond d'abord, Claude Code tue-t-il le hook encore en attente, ou le laisse-t-il finir ? Sans effet sur le démon (le relais est libéré au `PostToolUse` ou détaché à la fermeture de sa connexion), mais à observer.
- **Socket de contrôle refusé aux sessions** (lot 3) : un front lancé depuis un terminal d'une session DevMaestro (développement de l'app dans l'app) est refusé. Prévoir un message clair dans le front.
- **`dontAsk`** : la documentation de Claude Code indique que ce mode refuse automatiquement au lieu d'autoriser. Il est pour l'instant traité comme les modes dangereux (autorisation explicite dans `config.toml`), par prudence ; à reclasser après vérification avec le vrai CLI.
- **AppArmor sur Ubuntu 24.04 et plus** : `kernel.apparmor_restrict_unprivileged_userns = 1` interdit au bac à sable de Chromium de créer ses espaces de noms si l'app n'a pas de profil AppArmor (Electron s'arrête : « SUID sandbox helper binary was found, but is not configured correctly »). Le paquet de DevMaestro devra installer un profil `/etc/apparmor.d/devmaestro` (`userns,` sur le binaire de l'app), comme VS Code, Chrome ou Obsidian. En développement : profil sur le binaire Electron de `node_modules`, posé par l'utilisateur, ou lancement depuis un processus qui a déjà ce droit. Ne jamais livrer `--no-sandbox`.
