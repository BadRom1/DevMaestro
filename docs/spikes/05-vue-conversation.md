# Prototype n° 5 : vue conversation

- Objectif : savoir si l'on peut afficher une session comme une conversation, à la manière de Claude Desktop (fil de messages avec une vraie typographie, appels d'outils repliables, questions intégrées), **en gardant le vrai `claude` interactif** dans son PTY. La vue terminal reste disponible dans un onglet.
- Demande de l'utilisateur après le troisième essai de la v0.1 (2026-10-20). Cœur prévu de la v0.2.
- Outillage jetable : `spikes/05-vue-conversation/`.

## Deux voies

| Voie | Principe | Pour | Contre |
|---|---|---|---|
| **A. Transcript en direct** (piste principale) | Le vrai `claude` tourne dans son PTY ; le démon suit son transcript `.jsonl` au fil de l'eau et le front le dessine. La saisie part dans le PTY (collage + Entrée). | Garde la TUI d'origine, les commandes, les hooks, les ADR 0001 à 0003. | Format interne à Claude Code, qui peut changer ; pas de texte « en cours d'écriture » si le transcript n'est écrit qu'à la fin d'un message. |
| B. Mode programmatique | `claude -p --input-format stream-json --output-format stream-json` ou Agent SDK, comme Claude Desktop. | Flux structuré, texte en streaming. | Plus de TUI ni de slash commands interactives ; contredit l'ADR 0002 ; comportement différent de la session que l'utilisateur connaît. |

La voie B n'est étudiée que si la voie A échoue.

## Questions (voie A)

| N° | Question |
|---|---|
| Q1 | Quand une entrée est-elle écrite dans le transcript ? Délai entre l'affichage dans la TUI et l'écriture dans le `.jsonl`, pour un texte de Claude, un appel d'outil, un résultat, une question. Le texte est-il écrit au fil de l'eau ou seulement à la fin du message ? |
| Q2 | Quels types d'entrées et de blocs existent (message utilisateur, texte, réflexion, `tool_use`, `tool_result`, résumé de compaction, pièces jointes, méta), avec quels champs ? Lesquels faut-il pour reconstituer fidèlement la conversation ? |
| Q3 | Les sous-agents écrivent-ils dans des fichiers séparés, et comment les rattacher au message parent ? (Rejoint la Q12 du prototype n° 1.) |
| Q4 | Que se passe-t-il au `/clear`, à la compaction, au `--resume` (nouveau fichier ? suite du même ?) ? |
| Q5 | Saisie depuis un champ de l'app : la consigne tapée puis collée (règle du prototype n° 1, Q8) arrive-t-elle comme un prompt normal ? Slash commands, images collées ? |
| Q6 | Quoi montrer pendant que Claude écrit, si le texte n'arrive qu'à la fin : indicateur « Claude écrit… » à partir des hooks et de l'activité du PTY ? |
| Q7 | Coût du suivi : lecture incrémentale d'un fichier qui grossit (inotify), taille des transcripts réels, rendu d'une longue conversation (virtualisation). |
| Q8 | Stabilité du format : comparer des transcripts de plusieurs versions de Claude Code présentes sur le poste. |

## Outillage

Dans `spikes/05-vue-conversation/` (Python 3, bibliothèque standard uniquement) :

| Fichier | Rôle |
|---|---|
| `harness.py` | Hôte PTY : lance le vrai `claude` interactif (160×50) sans terminal, environnement nettoyé des marqueurs de session (listes lues dans `crates/core/src/daemon/launch.rs`), horodate chaque `read()` du PTY (`pty-index.jsonl` + `pty-raw.bin`), écrit le fichier de hooks passé par `--settings`, lance le suiveur, reçoit des commandes sur une FIFO. |
| `send.py` | Envoie à la FIFO : texte tapé, collage (*bracketed paste*), touches, prompt (texte, 1 s, Entrée). |
| `hooklog.py` | Hook de journalisation horodaté (14 événements, dont `PreCompact`, `SubagentStart/Stop`). |
| `follow.py` | **Suiveur de transcript** : découvre le dossier par `transcript_path` des hooks (et le cwd), inotify (ctypes) + scrutation de secours à 50 ms, suit les nouveaux `.jsonl` et `<session>/subagents/`, journalise chaque croissance du fichier et chaque ligne complète (type, sous-type, uuid, `message.id`, blocs, `timestamp` interne). |
| `screen.py` | Émulateur de terminal minimal : rejoue le flux du PTY jusqu'à un instant donné (pilotage, et mesure de « visible à l'écran »). |
| `analyze.py` | Chronologie fusionnée hooks / lignes du transcript / envois, et instant d'apparition à l'écran de marqueurs demandés à Claude, comparé à l'instant d'écriture de la ligne qui les porte. |
| `render.py` | Rendu HTML statique d'un transcript (sous-agents imbriqués, outils repliables, diff d'`Edit`, questions, collages, compaction, rendu de repli). `--stats` : temps de rendu et replis seulement, sans rien écrire. |
| `stats.py` | Statistiques en lecture seule (types, clés, tailles, versions, évolution par version) ; sert aussi d'inventaire Q2 sur nos sessions. |
| `anonymize.py` | Fabrique les fixtures à partir de nos sessions de test. |
| `fixtures/` | `transcripts/` (3 transcripts + 1 sous-agent avec son `.meta.json`, disposition identique à `~/.claude/projects/<projet>/`) et `chronologie/` (hooks, suivi, envois horodatés des sessions A, B, C). Anonymisées : chemins, identité, pièces jointes de contexte (valeurs vidées, types gardés), contenu des fichiers joints, résumé de compaction, commandes des hooks de l'utilisateur, requêtes d'API (définitions d'outils et de connecteurs), chemins de configuration et réécritures de commandes par ses hooks retirés. Pas de flux brut du PTY. ⚠ `suivi-B` relit au démarrage les lignes antérieures à la reprise (défaut corrigé ensuite) : leurs instants n'ont pas de sens. |

Exemple : `harness.py <sortie> <dossier> -- --session-id <uuid> --permission-mode acceptEdits`, puis `send.py <sortie> prompt "…"`, `screen.py <sortie>`, `analyze.py <sortie> --markers DEBUT,FIN`.

## Scénarios

1. Tour simple avec un texte long (le texte arrive-t-il par morceaux ?).
2. Tour avec lectures de fichiers, une commande Bash et une modification.
3. Question `AskUserQuestion` et permission.
4. Sous-agent lancé par l'outil `Agent`.
5. `/clear` puis nouveau prompt ; `/compact`.
6. Prompt envoyé depuis un champ externe (collage + Entrée).

## Critères de décision

- **Fidélité** : tout ce qui compte dans la TUI se retrouve dans le transcript (texte, outils, résultats, questions), à l'exception des dialogues éphémères déjà couverts par les hooks.
- **Délai** : une entrée apparaît dans la vue moins d'une seconde après la TUI, ou un indicateur d'écriture comble l'attente.
- **Robustesse** : un champ inconnu ou un type d'entrée nouveau n'empêche pas l'affichage (rendu de repli).
- Si ces critères tiennent : vue conversation en v0.2 par la voie A, avec un ADR. Sinon : étudier la voie B.

## Résultats

Relevés le 2026-10-20 avec Claude Code **2.1.304** (profil perso, Opus 5.5, effort moyen), dans un dépôt git jetable du scratchpad, par trois sessions pilotées sans terminal :

- **A** (`--session-id`, `acceptEdits`, Bash non autorisé) : texte long puis Read puis texte ; Read + Edit + Bash avec permission répondue dans la TUI ; `AskUserQuestion` ; collage court puis collage long (consigne tapée + contenu collé + Entrée) ; sous-agent Explore ; `/compact` puis un prompt ; `/clear` puis un prompt ; `/exit`.
- **B** (`--resume` de l'identifiant d'origine de A, après son `/clear`) : texte long, Read, texte.
- **C** (nouvelle session, `CLAUDE_CODE_EAGER_FLUSH=1`) : texte long, Read, texte.

### Fidélité constatée

Le rendu de `render.py` sur les sessions de test retrouve tout ce qui compte dans la TUI : prompts (collages compris, en entier), textes, appels d'outils avec résultats, diff de l'`Edit`, question `AskUserQuestion` avec la réponse choisie, sous-agent imbriqué sous son appel, notification de fin, compaction avec son résumé, commandes. Manquent, comme prévu : le texte en cours d'écriture (Q1), le contenu des réflexions (non conservé par Claude Code), les dialogues éphémères (permission, question en attente : couverts par les hooks), le spinner, le sondage et la suggestion de prompt.

### Recommandation : voie A

Les trois critères tiennent :

- **Fidélité** : tout ce qui compte est dans le transcript (ci-dessus), et les sous-agents se rattachent sans heuristique (Q3).
- **Délai** : une entrée complète arrive en général moins d'une seconde après la TUI (Q1, une exception à 1,4 s) ; le texte en train de s'écrire n'arrive qu'à la fin du message, avec un retard non borné : le critère ne tient que par l'indicateur fondé sur les hooks et, si on le veut, un aperçu brut de l'écran (Q6). L'ADR 0005 doit le dire.
- **Robustesse** : 16 versions lues sans erreur, cœur stable, rendu de repli démontré sur des entrées inventées (Q8).

La voie B n'est pas nécessaire : elle ne gagnerait que le texte en streaming, au prix de la TUI et de l'ADR 0002. Décision à consigner dans un **ADR 0005** (« la vue conversation lit le transcript ») : le transcript passe de source optionnelle (architecture § 6, rang 3) à source de la vue conversation, toujours en lecture tolérante ; les hooks restent la source de l'état.

Découpage proposé pour l'implémentation :

1. **Démon : suivi du transcript.** Étendre l'existant plutôt que doubler : le port `TranscriptSource` (`crates/core/src/ports/mod.rs`, aujourd'hui découverte des anciennes sessions) avec `adapters/transcripts.rs` et `domain/transcript.rs`, et le suivi des sous-agents par hooks (`domain/subagents.rs`) ; ajout d'un suivi en direct (port distinct ou méthode nouvelle) et d'un adaptateur fichier (`notify` + lecture incrémentale, reste de ligne partielle, reprise sur offset, jamais sur le mtime). Découverte par le `transcript_path` des hooks, bascule au `SessionStart` (`clear`, `resume`, `compact`), sous-agents par `SubagentStart` / `agent_transcript_path` / `.meta.json`. Normalisation en entrées stables, indépendantes du format : prompt, texte, réflexion, outil (+ résultat apparié), question, sous-agent, notification, compaction, commande, erreur, inconnu (repli). Publication au front : instantané au chargement (reprise, ancienne session), puis ajouts et mises à jour par `uuid` (un résultat complète son outil). Tests sur `spikes/05-vue-conversation/fixtures/`.
2. **Front : vue conversation.** Onglet « Conversation » à côté du « Terminal » : Markdown, outils repliables avec résumé d'une ligne, diff d'`Edit`, question et permission intégrées (cartes déjà alimentées par les hooks, ADR 0003), sous-agents repliés, séparateurs de compaction et de `/clear`, rendu de repli, liste virtualisée, gros résultats tronqués.
3. **Saisie.** Champ en bas de la vue : consigne tapée, contenu collé, Entrée (règle du prototype n° 1). Slash commands. Garde-fous : rien si le champ est vide ; pendant un dialogue de la TUI, selon la décision de l'ADR 0005 sur la lecture de l'écran (Q5) ; la file d'attente reste celle de Claude Code. Images plus tard.
4. **Indicateur d'écriture.** État « Claude écrit / outil X / sous-agent en cours / compaction » dérivé des hooks avec le temps écoulé (amender l'ADR 0002 pour déclarer `PreCompact`), puis, en option, l'aperçu des dernières lignes de l'écran tant que le message n'est pas dans le transcript.

### Ce qui reste supposé

- La règle exacte d'écriture de Claude Code (fin de message d'API) est déduite des instants, pas documentée ; une version future pourrait écrire plus tôt (tant mieux) ou plus tard.
- Pourquoi la TUI n'a pas déroulé le texte de la session B : non expliqué (une observation sur trois). Piste : dans B, réflexion, texte et `tool_use` portent un `timestamp` interne à 0,14 s de l'écriture (9,5 s d'avance pour la réflexion dans A), comme une réponse reçue d'un bloc.
- Non observés : images collées, sous-agent au premier plan, interruption (Échap) en plein texte (clé `isAbortedMidStream` vue dans les transcripts réels), compaction automatique, profil boulot en direct (le format est le même dossier), performances côté Rust et front.
